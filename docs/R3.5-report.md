# R3.5 — board workflow and monitoring under download load

Completed on 2026-10-02 using the connected NUCLEO-F446RE, its ST-LINK virtual
COM port at 115200 baud, and the 16 MHz HSI runtime configuration. OpenOCD
identified STM32 device `0x10006421` with 512 KiB flash, programmed the new
firmware and verified it. The full edit → build → upload → accept → monitor
workflow passed on hardware. R3 is complete; online state migration and
rollback remain R4.

Evidence: [structured board results](evidence/R3.5-board.json),
[programming and debugger logs](evidence/R3.5-debugger.txt). The structured
report includes firmware/package SHA-256 hashes, the edited test sources,
CLI results, timing samples, traffic counts and restoration status.

## Workflow and lifetime checks

The test builds a concrete ST edit through `plcpack` and the Rust/LLVM frontend:
change `LED := NOT BTN` to `LED := BTN`, and increment `N` by seven each scan.
The download reports generation 2 READY while generation 1 remains active.
After explicit activation, the product CLI's `monitor` command observes
`BTN=false`, `LED=false`, and `N=175` at scan 183 of the running generation 2.
The boot snapshot had correctly reported `BTN=false`, `LED=true`.

A second ST program uses all 64 DINT tags. Each scan increments `V00` and sets
`V01..V63` to `V00 + index`. This gives every paged snapshot an independently
checkable coherence invariant. Its package is 5,304 bytes. The CLI successfully
reads all 64 values through thirteen pages.

The hardware lifetime test pins generation 2's scan 145, stops reading for
250 ms, and observes the producer advancing to scan 173. It then activates a
three-tag program in the other slot and downloads a replacement into the
pinned snapshot's original slot. All remaining pages still contain the
original 64 names and values. A fresh enumeration observes generation 3 and
its three-tag schema. A separate 2.1-second stalled enumeration expires with
BUSY while the scan continues to advance.

## Timing and mixed traffic

The new debugger-visible `scan_body_cycles_last/max` counters measure the
complete application scan body: release bookkeeping, any activation, physical
input acquisition, protected native execution, state/output commit, snapshot
publication, status serialization, watchdog heartbeat and both stack probes.
The sample is immediately before `xTaskDelayUntil`; it excludes the final
measurement stores, the scheduler call itself and time blocked until release.
This definition makes the measured boundary explicit. Existing serial
`last_scan_us/max_scan_us` retain their narrower R3.4 meaning.

At 16 MHz, the measured counters give:

| Window | Maximum body | Last body | Release interval range | Missed releases |
| --- | ---: | ---: | ---: | ---: |
| Three-tag boot, idle engineering link | 1.628 ms | 1.627 ms | 9.664–10.000 ms | 0 |
| 64 tags, upload/activation then idle | 4.053 ms | 2.802 ms | 9.665–10.012 ms | 0 |
| 64 tags with mixed download/monitor traffic | 4.054 ms | 2.802 ms | 9.665–10.012 ms | 0 |

Each row uses a fresh reset. Maxima and interval ranges accumulate from that
reset, including initial scheduling and activation. The last-body samples are
read after the traffic window. These are observed values, not a worst-case
execution-time guarantee. OpenOCD halts only after each measurement window;
there are no debugger halts, breakpoints or memory reads during traffic.
The next window starts with another reset, so debugger pauses cannot pollute
its counters.

The mixed window lasted approximately 16.006 host seconds, with 1,607 scans
between its status samples. One serial host interleaved a READ_TAGS page after
each bounded download chunk; only one request was outstanding at a time.
During this window it completed:

- 11 downloads of a 5,304-byte image into the inactive slot, each reaching READY;
- 260 monitor pages, forming 20 complete 64-tag snapshots;
- zero scan faults, assertions, missed releases or UART receive errors.

The running generation stayed unchanged while inactive packages were replaced.
Every page was checked for generation/scan identity and all 64 values were
checked against the same captured `V00`. This exercises BEGIN, CHUNK and END
while the scan producer and paged reader are active, including validation and
slot sealing. The maximum body occupied about 40.5% of the 10 ms period.

Minimum unused stack observations in the mixed run were 408 scan-task words,
502 worker words and 928 comms words. Target link/layout checks passed with
26,016 bytes of privileged flash and 58,428 bytes of privileged RAM. The
raw remaining privileged RAM is 7,108 bytes. The linker reserves 4,096 of
those bytes for MSP, leaving 3,012 bytes for further static allocations.
R4 state reservations must fit that headroom or revise the layout deliberately.

## Reproduce

Build and validate before running the explicit board operation:

```sh
make test-scan test-engineering test-snapshot-thread
make target-build target-verify \
  FREERTOS_ARCHIVE=/path/to/kernel.tar.gz \
  ARM_PREFIX=/path/to/bin/arm-none-eabi-
python3 scripts/test_monitor_board.py --device /dev/cu.usbmodem2103 \
  --gcc-prefix /path/to/bin/arm-none-eabi- --openocd /path/to/openocd
```

The script is not part of ordinary host tests. It flashes the built firmware,
activates test programs, and resets back to the normal boot program in
`finally`. Reports and raw logs are written under `build/monitor-board/`.
The recorded run ended with generation 1 running, fault zero, and no missed
releases. The installed firmware retains the new monitor and timing support.
Host scan tests, engineering/serial tests, AddressSanitizer,
UndefinedBehaviorSanitizer and snapshot ThreadSanitizer stress also passed.
