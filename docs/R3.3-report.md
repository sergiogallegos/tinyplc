# R3.3 report — USB serial download and native activation

Completed 2026-10-01 on the connected NUCLEO-F446RE. The complete path now works:
ST → Rust frontend → LLVM AOT → fixed-slot native package → USB serial staging
→ explicit activation → unprivileged execution under the C/FreeRTOS supervisor.
Status reports the actual generation and execution/fault outcome. Coherent tag
monitoring, tag writes, state migration and rollback remain future work.

## Implemented

- Bounded C stream framing, CRC/replay/timeout handling and INFO, download,
  activate and status dispatch. The USART2 RX interrupt publishes bytes and
  arrival timestamps into a fixed ring; parsing/copying runs in a lower-priority
  static comms task. Firmware advertises only implemented commands (`0x11f`).
- Per-task MPU ownership: comms maps only its reserved inactive slot writable/XN
  during END and seals it afterward; the native worker sees only the active
  slot RX. The scan task maps code read-only/XN.
- Scan-boundary activation recreates the suspended static worker, resets state,
  selects the validated schema/bindings and publishes the read-only entry/count/
  generation descriptor. Both slots and 1..64 tags are supported. A failed first
  scan latches safe outputs and a rejected outcome; recovery requires an explicit
  fresh activation. No automatic rollback is claimed.
- Rust `plctool` uses std plus system `stty`, with no third-party Rust crates.
  It checks compatibility/placement, downloads to READY, separately activates,
  confirms the actual outcome and emits JSON. Only exact chunk retries are
  automatic; other mutation timeouts require status reconciliation.

The full ownership and command guide is [engineering-transport.md](engineering-transport.md).

## Host verification

Full `make test`, Clippy with warnings denied, and the integrated board build/ELF
checks passed. New ASan/UBSan tests cover fragmented frames, rejected lengths,
embedded-frame recovery, timeout/wrap behavior, malformed requests and unsupported
commands. A POSIX pseudo-terminal runs the actual Rust CLI against the C engine,
including an intentionally dropped chunk ACK, READY/ACTIVE separation and
wrong-slot preflight rejection. Existing package/loader and native semantic
regressions continue to pass.

The real Mac serial test caught a detail the PTY did not: configuring via stty
before opening the device allowed settings to reset on last close, leaving a
blocking read. The CLI now holds the device open while configuring it. The
receive ring records arrival times rather than comms processing times so a
busy scan cannot incorrectly extend the wire inter-byte timeout.

## Final hardware evidence

[Structured board evidence](evidence/R3.3-board.json) contains the final firmware
hash, package hashes, command results and debugger samples. The final script
completed successfully and restored normal engineering firmware afterward.

- A corrupt frame was dropped, an expired partial frame recovered, unsupported
  operations and wrong widths were rejected, and duplicate chunks were accepted
  without advancing twice. Corrupt package END returned CRC_ERROR.
- Downloading the edited package left boot generation 1 active. Explicit
  activation switched to generation 2 in B. Reordered tags were respected:
  internal N advanced to 33, BTN was FALSE and physical LD2 was OFF. This differs
  from the normal boot example's ON output with BTN released.
- A real compiler-generated **64-tag** program executed from A, advanced V00 to
  33 and kept the unbound LED safe. It was then replaced with the normal program.
- A first-scan ST divide-by-zero produced fault 5, rejected the activation and
  committed neither the proposed TRUE output nor N=123. A fresh download and
  activation recovered execution.
- Nine downloaded native fault cases alternated A/B placements: privileged RAM
  write, active code write, direct kernel SVC, infinite execution, invalid PSP,
  stacking fault, flash gateway write, inactive-slot write and descriptor write.
  Expected statuses were 259/260/258/261. Contained cases kept N=3 and forced
  output FALSE; invalid contexts reset via IWDG and returned to the fault-latched
  boot generation. Every case was followed by successful fresh activation.

Jitter now measures actual release against the scheduled FreeRTOS tick, including
sub-tick phase; restored status reported +31 µs. These are observations, not
worst-case guarantees. The deadline has finite interrupt latency. Debugger
samples briefly halt execution and freeze the watchdog; they do not constitute
a continuous real-time run. CFSR debug fields retain the latest CPU fault and
may be older than a later arithmetic/deadline event; the protocol fault code
identifies the current scan fault.

## Reproduce

Use the pinned local toolchain and kernel archive; LLVM tools must be on PATH.

```sh
make test ARM_PREFIX=/path/to/bin/arm-none-eabi-
make target-build target-verify FREERTOS_ARCHIVE=/path/to/kernel.tar.gz ARM_PREFIX=/path/to/bin/arm-none-eabi-
```

The following is an **explicit lab-board operation**: it flashes firmware,
uploads and activates fault fixtures, exercises watchdog reset, and restores
normal firmware in `finally`. It is not part of ordinary host tests.

```sh
python3 scripts/test_engineering_board.py --device /dev/cu.usbmodem2103 \
  --openocd /path/to/openocd --gcc-prefix /path/to/bin/arm-none-eabi- \
  --clang /path/to/clang
```

The script preserves its local report/logs under `build/engineering-board/`.
The reviewed final report is copied into `docs/evidence/` with repository-relative
paths. A detected USB device alone is not accepted as hardware evidence.
