# R4.1 — online state semantics review

Completed 2026-10-02. The [online state contract](online-state.md) defines the
first R4 task. This is a reviewed specification, not runtime implementation or
hardware acceptance. The running board and capability advertisement are unchanged.

## Decisions frozen for R4.2

- Healthy activations migrate committed VAR cells by canonical name and exact
  type at the application boundary. Additions, renames and type/class changes
  initialize to zero. Faulted-source activation remains a cold recovery path.
- Inputs are freshly sampled and frozen; output cells start zero on activation
  and restoration. Physical output continuity is not guaranteed.
- Both contexts remain reserved through one complete candidate trial. Only a
  contained first-scan failure triggers automatic restoration, at a later
  scheduled release. No second invocation or repeated recovery loop is allowed.
- Rollback restores the saved pre-activation state, consumes PREVIOUS and
  retires the departing image. BEGIN success explicitly retires rollback
  eligibility even if its later transfer fails.
- Current execution fault and retained update failure remain distinct.
  Existing GET_STATUS fields keep their meanings. A planned read-only
  GET_UPDATE_STATUS command records the rejected trial and recovery cause;
  its field table and compatibility rule are specified for R4.2 generation.
- R4 additions receive a 1,024-byte static-storage design cap. Per-slot schemas
  remain pinned and reused; no third schema/state context is introduced.

The normative document contains migration examples, slot/request transitions,
status outcomes, a 53-byte proposed diagnostic response and ten implementation
acceptance cases. It also identifies the need to register the boot image's
full descriptor/schema for rollback, beyond R3's monitoring-only metadata.

## Evidence reviewed and correction

Reviewed against the current [scan transaction](../runtime/src/scan.c),
[loader ownership](../runtime/include/tinyplc/loader.h),
[board request/publication adapter](../port/nucleo_f446re/native/engineering_board.c),
[native ABI](native-abi.md), [wire contract](wire-format.md), and the
[R3.5 board results](evidence/R3.5-board.json).

The [linker layout](../port/nucleo_f446re/native/memory.ld) reserves 4 KiB for
MSP beyond allocated privileged data. R3.5's 58,428-byte allocation therefore
leaves 65,536 − 58,428 − 4,096 = **3,012 bytes** for additional static data.
The original 7,108-byte figure was the raw gap including MSP. The R3.5 report
and memory-planning documentation now distinguish those quantities. The new
1,024-byte planning cap leaves 1,988 bytes before further alignment or other
changes; only a later integrated link can establish actual R4 usage.

Documentation links and the proposed response offsets/widths were checked.
No firmware, generated wire constants, package semantics or advertised
capabilities changed. Runtime tests were not rerun for this documentation-only
step; no R4 migration/rollback execution is claimed.

Next is R4.2: implement bounded migration/checkpoint storage, owned request
reservations, trial and rollback transitions, retained diagnostics, CLI handling
and the specified host/concurrency checks. R4.3 then verifies state transfer,
fault recovery, output behavior and whole-scan timing on the board.
