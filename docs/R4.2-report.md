# R4.2 — migration, trial and rollback implementation

Implemented 2026-10-02 under the [R4.1 state contract](online-state.md).
The portable C transaction and STM32 adapter now preserve compatible VARs,
reserve both slots through a first-scan trial, and support explicit and automatic
rollback. The Rust CLI adds `rollback` and `update-status`. Hardware acceptance
is recorded separately in [R4.3](R4.3-report.md).

## Implementation and ownership

[`update.c`](../runtime/src/update.c) owns a bounded transaction with a saved
64-cell checkpoint, a 64-byte migration map, exact slot/generation identities,
phase/outcome fields and retained first/recovery diagnostics. Successful healthy
activation copies only same-name/same-type VARs at the application boundary;
new/incompatible variables and outputs start zero. Faulted sources cold-start.
The boot module is registered with complete entry/schema/binding metadata, so
it can be restored without retaining pointers into reusable slot A.

The comms task reserves the immutable schemas in short critical sections, then
constructs the name/index map preemptibly. The scan cannot consume a partially
built map. The scan owner revalidates identities, slot states, map entries and
canonical state before applying the map and installing a fresh worker.
No name-search loop or state copy runs with interrupts masked. INFO's mutable
slot words and the retained diagnostic are copied under short serialization.

The transaction stays busy through `xTaskDelayUntil`. At the next release the
scan resolves the preceding trial before preparing another generation. A late
body/release overrun discards candidate VAR writes before publishing corrected
fault values; it does not release the old checkpoint prematurely. This also
keeps rollback from racing BEGIN after an apparently successful native return
but before trusted work and scheduler admission have finished.

A contained first-scan fault forces outputs FALSE and restores the saved source
on a later release. A failed restoration stays faulted with no retry loop.
Explicit rollback restores the saved pre-update VARs, zeros output state and
consumes PREVIOUS. A successful BEGIN retires a checkpoint permanently even if
that transfer later fails. The update record survives rejected requests and
ordinary later faults, while GET_STATUS describes current execution.

## Protocol and CLI

Protocol/package versions and ABI are unchanged. R4 advertises capabilities
`0x7` (unsigned lab, migration, rollback) and command mask `0x37f`. WRITE_TAG is
still unsupported. GET_UPDATE_STATUS is the additive command 10 with a 53-byte
success payload. Its exact offsets are generated from
[`contract/wire.json`](../contract/wire.json); C/Rust golden-frame consumers
check the new request/response alongside the existing frames.

`plctool DEVICE rollback` queues PREVIOUS and polls for its actual result.
`plctool DEVICE update-status` prints request kind, phase, outcome, source and
requested generations, rejected trial, first/recovery fault, source position,
and completion generation/scan. Automatic restoration of the old program makes
`activate` return nonzero, even when current execution has recovered. Older R3
controllers remain usable for their advertised operations.

## Host and target checks

The full host suite passed with the pinned ARM linker path. Focused engineering
and ThreadSanitizer checks were also run after the final lifetime/correction
changes. Reproduce with:

```sh
make test ARM_PREFIX=/path/to/bin/arm-none-eabi-
make test-update-thread test-snapshot-thread
make target-build target-verify \
  FREERTOS_ARCHIVE=/path/to/kernel.tar.gz \
  ARM_PREFIX=/path/to/bin/arm-none-eabi-
```

The ASan/UBSan transaction suite checks reordered and 64-tag migration,
canonical BOOL/DINT values, type/class changes, boundary-time capture, stale
slot/generation/map rejection, cold activation from FAULT, saved-state rollback,
first-scan recovery, recovery failure, later faults, and late-overrun discard
before fault publication. It also exercises 4,000 serialized reservation/
retirement schedules. The pthread harness runs 2,000 concurrent activation and
rollback pairs while the scan advances and comms reads coherent diagnostics;
the same test passed ThreadSanitizer without race reports. The existing owned
snapshot stress and serial CLI/transfer regression tests still pass.

The update object is 432 bytes on the host and 424 bytes on Cortex-M4, below
the 1,024-byte design cap. Integrated privileged RAM is 58,740 bytes, a 312-byte
increase from R3.5 after reusing the loader's boot schema storage. With the
separate 4,096-byte MSP reservation, 2,700 bytes remain for additional static
data. Privileged flash is 28,656 bytes; call/gateway flash is 528 bytes.
Target link, protected gateway and negative placement/overflow checks passed.
Compiler-reported frames are 56 bytes for planning, 80 for preparation and
32 for completion; these are per-function estimates, not full stack bounds.

No new language types, tag writes, persistence, network transport, or guarantee
of unchanged physical outputs is implied. R4.3 exercises the actual downloaded
artifacts, guard faults and measured scan body on the board.
