# R4.3 — hardware migration and rollback acceptance

Completed 2026-10-02 on the NUCLEO-F446RE at 16 MHz, using its 115200-baud
ST-LINK serial link. The [R4.2 implementation](R4.2-report.md) passed the update/
fault matrix and the existing download/monitor stress suite. Both final reports
match the SHA-256 of the built firmware. Each suite finished with generation 1
running normally, fault zero and no pending request.

Evidence: [update/fault matrix](evidence/R4.3-board.json),
[mixed traffic](evidence/R4.3-monitor.json), and
[programming/timing logs](evidence/R4.3-debugger.txt). Reports include exact test
sources, artifact hashes, CLI results, scan IDs, retained faults and restoration
status. The new firmware remains installed with the normal boot program active.

## State and fault results

The script verifies actual Rust/LLVM packaged programs through `plctool`:

| Case | Verified result |
| --- | --- |
| Reordered compatible N, new NEW, BOOL→DINT FLAG | N follows the migrated checkpoint plus seven per scan; NEW starts zero; FLAG resets to DINT zero |
| Unassigned candidate output | LED starts FALSE despite the previous program's output |
| Explicit rollback after many candidate scans | Restored source resumes its saved pre-update N, not the candidate's newer value; PREVIOUS is consumed |
| First-scan division fault after dirtying N/output | Candidate changes discarded; source resumes on the next release; retained fault 5 remains separate from current fault 0 |
| Rejected BEGIN, then valid BEGIN with failed transfer | Rejected reservation preserves rollback; accepted reservation retires it permanently |
| 64 reordered DINTs with long common name prefixes | Every value preserves its identity and offset; restored values match the saved checkpoint |
| First-scan protected code write | Fault 259; automatic restoration of firmware-linked generation 1 succeeds |
| First-scan infinite loop | Deadline fault 258; bounded recovery restores generation 1 without retrying the candidate |
| Invalid native exception stack | Watchdog reset; generation 1 boots fault-latched with fault 261; RAM update record/checkpoint is gone |
| Activation from faulted boot into a failing image | Cold start, no fallback checkpoint, candidate remains faulted/REJECTED |
| Failure of automatic restoration | Original and recovery faults retained; restored generation stays faulted, output tag FALSE, no retry loop |
| Failure of explicit rollback | Rollback target stays faulted, checkpoint consumed, departing slot EMPTY |
| Fault after a successful trial | No automatic rollback; explicit rollback can still recover PREVIOUS |

Migration assertions use the global scan IDs to calculate exact expected values
rather than testing only that a counter is nonzero. The 64-tag test reverses
all declarations and uses names with a long shared prefix. This exercises both
comms-side map construction and scan-side revalidation/application.

Restoration failure is deterministic: the old program runs successfully with a
nonzero internal counter and an output set TRUE, but deliberately divides by
zero when that saved counter meets the required zero output image on restoration.
Both automatic and explicit paths retain their faults and remain responsive.
These checks observe published output tags and the execution state; they are
not an independent electrical measurement of PA5.

The native assembly probes have an explicit `FIRST_SCAN_FAULT` test build flag.
Their default historical mode still faults on scan four. The first-scan mode
is necessary to distinguish trial recovery from ordinary later fault latching.
Intentional deadline/watchdog cases are separate from no-missed-release timing
windows; they are not counted as normal successful scans.

## Whole-body timing and concurrent traffic

The body counter uses the boundary documented in [scan-runtime.md](scan-runtime.md):
release work, prior trial resolution, any state preparation/worker recreation,
native execution, commit, snapshot/status publication, heartbeat and stack checks,
ending before scheduler wait. Blocking time and the scheduler call itself are
excluded. Maxima include activation/restoration, and are observed values rather
than worst-case bounds.

| Fresh-reset measurement window | Maximum cycles | Maximum body | Missed releases / UART errors |
| --- | ---: | ---: | --- |
| Small-schema migration and rollback workflow | 46,384 | 2.899 ms | 0 / 0 |
| 64-tag long-name reorder and restoration | 90,063 | 5.629 ms | 0 / 0 |
| 64-tag execution with mixed download/monitor traffic | 68,566 | 4.285 ms | 0 / 0 |

The longest observed normal body occupies about 56.3% of the 10 ms period.
The mixed window lasted 16.029 host seconds, advancing from scan 149 to 1760:
1,611 scans while completing 11 inactive-slot downloads and 260 monitor pages,
forming 20 full 64-tag snapshots. No running generation changed during that
load window. Its observed release intervals ranged from 9.664 to 10.012 ms,
including the initial scheduling interval. The reader also survived activation
and reuse of its original slot, and expired correctly after a 2.1-second stall.

Debugger halts occur only after measurement windows, with a fresh reset before
the next window. Mixed-run unused stack observations were 438 scan-task words,
502 worker words and 928 comms words. The integrated firmware uses 58,740 bytes
of privileged RAM, leaving 2,700 bytes after the separate 4 KiB MSP reservation.
Target layout checks and host sanitizer/concurrency checks are in the R4.2 report.

## Reproduce

```sh
make test ARM_PREFIX=/path/to/bin/arm-none-eabi-
make test-update-thread test-snapshot-thread
make target-build target-verify \
  FREERTOS_ARCHIVE=/path/to/kernel.tar.gz \
  ARM_PREFIX=/path/to/bin/arm-none-eabi-
python3 scripts/test_update_board.py --device /dev/cu.usbmodem2103 \
  --gcc-prefix /path/to/bin/arm-none-eabi- --openocd /path/to/openocd
python3 scripts/test_monitor_board.py --device /dev/cu.usbmodem2103 \
  --gcc-prefix /path/to/bin/arm-none-eabi- --openocd /path/to/openocd
```

These are explicit lab-board operations, not part of host-only tests. They flash
the built image, activate test programs, and reset back to the normal boot
program in `finally`. The R4 runner additionally injects native access, deadline
and watchdog faults. Local reports are under `build/update-board/` and
`build/monitor-board/`. The earlier R3.3 runner records historical cold-start
expectations; use the R4 runner for migration-aware acceptance.

R4 is complete for this profile. R5 begins by choosing a language, debugging or
target extension from an actual need, with its own resource and acceptance plan.
