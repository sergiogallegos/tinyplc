# R3.2 report — Rust packager and portable C staging loader

Completed 2026-10-01. ST source now produces a native package through the
Rust frontend, LLVM and fixed-slot linker. The portable C validator and staging
loader consume those exact bytes. This milestone stops at READY; there is no
serial download endpoint or execution of downloaded code on the board yet.

## Implemented

- [`plcpack`](../packager/README.md), using only project-owned Rust crates and
  standard library, invokes installed LLVM/GNU ld and extracts the compiler's
  exported schema from the resulting ELF. No separate hand-edited tag file.
- [Full C package validation](native-loader.md): identity, exact compatibility,
  firmware-owned unsigned policy, slot placement, checked ranges, text entry,
  CRCs, canonical unique names, types/classes, physical binding ownership and
  reserved fields. No received address becomes a host/MCU pointer.
- Static package staging and separate metadata/code storage, contiguous chunks,
  exact latest-chunk retry, expiry, generation/ID exhaustion, immutable READY
  results and active-slot preservation. New BEGIN explicitly retires a READY
  or PREVIOUS candidate before reusing its slot; pending/active ownership blocks
  conflicting reuse. No activation or concurrent-owner API is implied.
- A target cross-build check with a 24 KiB static loader budget and project-owned
  freestanding byte primitives. The board port now has memcmp/memmove alongside
  memcpy/memset for future linkage; their behavior is host-tested independently.

The compiler example packages are **384 bytes**: 80-byte header, 184-byte
payload and three 40-byte tag records. Both A and B variants validate through
C; the B variant also passes the full staging lifecycle. Additional ST with
only internal BOOL/DINT variables verifies schema extraction beyond BTN/LED/N.

## Verification

Passed full `make test` plus `loader-target-check` using LLVM 23.1.2 and pinned
ARM GCC 13.3.1. The existing board firmware build/ELF placement checks also
passed after adding freestanding byte primitives; no flash was performed.
Clippy passed with warnings denied. New coverage includes:

- Actual Rust-built A/B artifacts accepted by the C validator; repeated builds
  produce identical bytes. Compiler errors preserve an existing output file.
- Every header policy/resource field, re-CRC'd incompatible images, bad CRCs,
  malformed ranges, noncanonical/duplicate names, invalid bindings and widths.
- Maximum 19,024-byte package with 64 tags and full 16 KiB payload, staged into
  separate code/metadata storage under ASan/UBSan.
- Partial END, wrong/stale IDs, conflicting duplicates, out-of-order chunks,
  zero/oversized chunks, exact expiry and clock wrap, pending ownership and
  generation/transfer counter exhaustion. Active code remains unchanged.
- 4,000 deterministic package mutations per ordinary staging fixture, and
  2,000 ELF mutations plus every synthetic ELF truncation in Rust tests.
- Freestanding memmove overlap cases in both directions and byte-operation
  comparisons against the host C library, under ASan/UBSan.

The [ARM target evidence](evidence/R3.2-loader-target.json) records **24,240 bytes
of BSS, zero data and 2,512 bytes of text** in the standalone relocatable link,
with no undefined symbols. Individual validator/END frames are 80 bytes each;
these are compiler frame reports, not whole-task stack measurements. The code
slots are caller-owned and are not included in that loader-state figure.

```sh
make test ARM_PREFIX=/path/to/bin/arm-none-eabi-
make loader-target-check ARM_PREFIX=/path/to/bin/arm-none-eabi-
./target/debug/plcpack examples/button_led.st --slot B -o build/button-b.tplc \
  --clang /path/to/clang --ld /path/to/arm-none-eabi-ld
```

LLVM tools must be on PATH for the existing native differential suite. No
command downloads a dependency, flashes a board or executes a package.

## Limits and next task

The C APIs require one serialized owner and stable, caller-owned buffers. Host
arrays substitute for code slots in these tests. The ARM build is relocatable,
not a full runtime integration: MPU staging permissions, worker quiescence,
READY-to-ACTIVE transitions, dispatch descriptor and comms stack still need
board wiring and measurement. CRC validates corruption, not authorization or
native-code behavior. The existing R2 privilege/deadline boundary remains
necessary. No claim of production safety, migration or rollback is added.

Next is **R3.3**: bounded UART framing, engineering host commands and board
staging/activation integration. Snapshots/monitoring and then R4 online-state
migration/rollback follow. The board was not flashed during R3.2; its previously
restored button/LED firmware remains the last installed image.
